## 2024-09-24 - Resolving PostgreSQL N+1 correlated subqueries using LEFT JOIN LATERAL
**Learning:** In the root songs query, using standard correlated subqueries in the SELECT clause (like \`SELECT AVG(score)\`, \`SELECT COUNT(*)\` etc.) creates N+1 per-row execution overhead. Consolidating multiple aggregates on the same table (e.g. ratings) into a single \`LEFT JOIN LATERAL\` query significantly cuts down redundant index lookups and acts as a better alternative. However, we should avoid doing this blindly when there's an \`ORDER BY\` on fully aggregated values (like the popular endpoint) because pushing lateral joins before ordering can cause early row limits to be bypassed, introducing nested loop regressions.
**Action:** Always refactor correlated N+1 \`SELECT\` aggregates pointing to the same table into a single \`LEFT JOIN LATERAL\`.
## 2024-09-24 - Safely Resolving PostgreSQL N+1 correlated subqueries using LEFT JOIN LATERAL
**Learning:** In the root songs query, using standard correlated subqueries in the SELECT clause creates N+1 per-row execution overhead. Consolidating multiple aggregates on the same table (e.g. ratings) into a single \`LEFT JOIN LATERAL\` query significantly cuts down redundant index lookups. However, if applied directly to the \`FROM\` clause before an \`ORDER BY\` and \`LIMIT\`, Postgres will execute the lateral join for every matched row in the database before sorting, causing a massive performance regression. The safe approach is to isolate the base query (with search, sort, and limit) in a subquery or CTE, and *then* join the \`LATERAL\` aggregate subqueries to the final paginated results.
**Action:** When refactoring correlated N+1 \`SELECT\` aggregates pointing to the same table into a single \`LEFT JOIN LATERAL\`, always ensure the base query's \`ORDER BY\` and \`LIMIT\` are applied first (e.g., via a subquery) to prevent full-table nested loops.
